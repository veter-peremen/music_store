# Музыкальный магазин

Учёт винила в магазине: что стоит на полках, кто это записал, сколько экземпляров осталось и как они расходятся.

Система отвечает на четыре повседневных вопроса продавца:

- **Что у нас есть?** — каталог пластинок с исполнителями и жанрами.
- **Сколько осталось?** — остаток по каждой позиции, всегда актуальный.
- **Что пришло и что ушло?** — история поступлений и продаж.
- **Что продаётся лучше всего?** — отчёт по лидерам продаж.

Это учебный проект курса «Методология и практики DevOps» (Московский Политех). Приложение — HTTP API поверх PostgreSQL; оно будет развиваться от лабораторной к лабораторной, обрастая инфраструктурой, контейнерами и автоматическими проверками.

## Главное правило

**Нельзя продать больше, чем лежит на складе.**

Звучит очевидно, но именно вокруг этого правила построена вся механика продаж. Продажа выполняется одной транзакцией: проверяем остаток, записываем цену, списываем со склада. Если товара не хватает — не происходит ничего, остаток остаётся прежним, а в ответ приходит `409` с объяснением, сколько есть и сколько запросили.

Из этого правила следуют два других решения:

**Цена хранится снимком.** Каждая продажа помнит цену, по которой её провели. Переоценка меняет ценник на будущее и не переписывает прошлые сделки — иначе выручка за прошлый месяц менялась бы задним числом.

**Ничего не удаляется — всё уходит в архив.** Музыкантов и пластинки нельзя стереть, их можно только убрать из каталога и вернуть обратно. Продажи ссылаются на пластинки, и физическое удаление карточки унесло бы с собой историю продаж. Архивация музыканта забирает в архив и его пластинки; вернуть их можно по одной, когда решите снова выставить на полку.

## Стек

Node.js и Express для API, PostgreSQL для данных, Knex для миграций и запросов, zod для проверки входящих данных, Jest и Supertest для тестов, ESLint и Prettier для единообразия кода.

## Запуск локально

Понадобятся **Node.js 20+** (`node --version`) и **PostgreSQL 16** (`psql --version`).

```bash
npm install                              # зависимости
cp .env.example .env                     # конфигурация — впишите свои параметры БД
createdb -U postgres music_store         # создать базу, один раз
npm run migrate                          # создать таблицы
npm run seed                             # демонстрационные данные, по желанию
npm start                                # запустить
```

Сервер поднимется на `http://localhost:3000` — порт берётся из `PORT` в `.env`.

Проверить, что всё живо:

```bash
curl http://localhost:3000/health         # процесс отвечает
curl http://localhost:3000/health/ready   # и база доступна
```

Первый адрес не трогает базу, второй проверяет соединение с ней. Если первый отвечает, а второй возвращает 503 — приложение работает, но до базы не достучалось: проверьте `DB_*` в `.env`.

Список всех маршрутов отдаёт корень: `curl http://localhost:3000/`

### Если не хочется ставить PostgreSQL

```bash
docker compose up -d      # поднимет postgres:16 с параметрами из .env
npm run migrate
npm start
```

Остановить базу: `docker compose down`.

### Когда что-то пошло не так

| Что видите                                    | В чём дело                                                                                                                                      |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `EADDRINUSE: address already in use :::3000`  | порт занят. Запустите на другом: `PORT=3001 npm start`                                                                                          |
| `база данных "music_store" не существует`     | пропущен `createdb -U postgres music_store`                                                                                                     |
| `password authentication failed`              | неверные `DB_USER` или `DB_PASSWORD` в `.env`                                                                                                   |
| `/health/ready` отдаёт 503                    | PostgreSQL не запущен либо `DB_HOST` / `DB_PORT` смотрят не туда                                                                                |
| `make: command not found`                     | на Windows `make` не установлен — пользуйтесь `npm run`, см. таблицу ниже. Поставить: `choco install make`                                      |
| проверки падают на файлах, которых не трогали | окончания строк. Один раз выполните `git add --renormalize .`                                                                                   |
| вместо русского текста в базе мусор           | кириллицу нельзя слать curl'ом прямо в командной строке на Windows — [подробности](docs/SCENARIOS.md#важно-кириллица-в-теле-запроса-на-windows) |

Остановить сервер — `Ctrl+C`. Если запускали в фоне, найдите процесс: `netstat -ano | grep :3000`

## Команды

Методичка требует единый интерфейс через `make`:

| Команда                 | Что делает                            | Без make                                           |
| ----------------------- | ------------------------------------- | -------------------------------------------------- |
| `make setup`            | зависимости и `.env`                  | `npm install`                                      |
| `make run`              | запуск                                | `npm start`                                        |
| `make test`             | тесты                                 | `npm test`                                         |
| `make quality`          | форматирование и статический анализ   | `npm run format:check && npm run lint`             |
| `make migrate`          | применить миграции                    | `npm run migrate`                                  |
| `make rollback`         | откатить последнюю миграцию           | `npm run migrate:rollback`                         |
| `make seed`             | демонстрационные данные               | `npm run seed`                                     |
| **`make verify`**       | **всё вместе — обязательно перед PR** | `npm run format:check && npm run lint && npm test` |
| `make up` / `make down` | контейнер с базой                     | `docker compose up -d` / `down`                    |

## Конфигурация

Только через переменные окружения, шаблон — в `.env.example`:

| Переменная                | Что задаёт        | По умолчанию            |
| ------------------------- | ----------------- | ----------------------- |
| `NODE_ENV`                | окружение         | `development`           |
| `PORT`                    | порт HTTP-сервера | `3000`                  |
| `DB_HOST` / `DB_PORT`     | адрес PostgreSQL  | `127.0.0.1` / `5432`    |
| `DB_USER` / `DB_PASSWORD` | учётные данные    | `postgres` / `postgres` |
| `DB_NAME`                 | имя базы          | `music_store`           |

Файл `.env` перечислен в `.gitignore` и в репозиторий не попадает — там пароли. В репозитории живёт только `.env.example` с безопасными заглушками.

## Правила внесения изменений

Раздел обязателен для всех участников. Смысл простой: любое изменение считается потенциально ошибочным, пока не доказано обратное — неважно, кто его написал.

### Путь изменения

1. **Задача.** Всё начинается с issue, где сказано, какой результат нужен.
2. **Ветка.** От `main`: `feature/…` для новой функции, `fix/…` для исправления, `docs/…` для документации.
3. **Коммиты.** Несколько штук, каждый — законченная мысль. Формат `feat:`, `fix:`, `docs:`, `test:`, `chore:`, `refactor:`. В сообщении объясняйте **зачем**, а не пересказывайте diff: что изменилось, видно и так.
4. **Проверка у себя.** `make verify` должен быть зелёным **до** пуша.
5. **Pull Request.** Опишите, что меняется, зачем и как проверено. Прямой push в `main` запрещён.
6. **Чтение.** PR смотрит другой участник. Замечания закрываются новыми коммитами в ту же ветку.
7. **Слияние.** Только с зелёными проверками и одобрением. После — ветка удаляется.

### Обязательная проверка

```bash
make verify
```

Внутри — три вещи: `format:check` (Prettier), `lint` (ESLint, ноль ошибок) и `test` (все тесты Jest). Зелёный результат нужен и перед созданием PR, и перед слиянием.

### Чего делать нельзя

- **Удалять или отключать тесты**, чтобы проверка прошла. Красный тест — это сообщение, а не препятствие.
- **Ослаблять анализаторы**: отключать правила, снижать пороги, добавлять исключения ради «зелёного».
- **Коммитить секреты**: `.env`, пароли, ключи, токены, дампы с реальными данными.
- **Пушить напрямую в `main`** и делать туда `force-push`.
- **Править применённые миграции.** Ошибка в миграции исправляется новой миграцией — иначе у коллег база разойдётся с вашей.
- **Незаметно менять файлы приёмки** — `Makefile`, `migrations/`, `docker-compose.yml`, `TZ.md`, `.github/`. Такие правки выносятся в описание PR отдельным пунктом.

### Когда изменение принято

Одновременно выполнено всё:

1. Задача закрыта тем PR, который её решает.
2. `make verify` зелёный на ветке.
3. PR прочитан другим участником, замечания закрыты.
4. Изменения файлов приёмки перечислены в описании PR.
5. Секреты и локальные файлы в diff не попали.
6. Ветка слита в `main`; релизная точка при необходимости помечена тегом.

## Кто чем занимается

Проект делится на три зоны — так требует методичка, и так удобнее не мешать друг другу:

- **Каталог** — музыканты, жанры, карточки пластинок, архивация и возврат.
- **Склад и продажи** — поступления, продажи, остатки и правило «не продать больше, чем есть».
- **Инфраструктура и качество** — миграции, конфигурация, тесты, `make`, CI.

## Что внутри

```
src/
  domain/        чистая логика предметной области — считается и тестируется без базы
  routes/        HTTP-маршруты по ресурсам
  validation/    схемы проверки входящих данных
  middleware/    обработка ошибок и неизвестных маршрутов
migrations/      версионированная схема базы
seeds/           демонстрационные данные
tests/           автоматические тесты
docs/            описание API, схема данных, сценарии, разбор конфликта слияния
```

Правила предметной области намеренно вынесены в `src/domain/` и не знают ни про HTTP, ни про базу. Поэтому «нельзя продать больше остатка» проверяется обычным тестом без поднятой PostgreSQL.
