# Техническое задание — «Музыкальный магазин» (складской учёт винила)

Учебный сквозной проект курса «Методология и практики DevOps». Документ фиксирует пункты 2–3 ЛР1: назначение системы, категории пользователей, сценарии, обязательные правила, а также функции, сущности, связи, ограничения, ошибки и требования к хранению данных.

## 1. Назначение системы

Информационная система складского учёта магазина виниловых пластинок. Хранит каталог пластинок с привязкой к музыкантам и жанрам, ведёт остатки на складе, регистрирует поступления и продажи, позволяет редактировать карточки пластинок, музыкантов и список жанров.

Ключевая ценность — всегда актуальный остаток по каждой позиции и корректная история движений (поступления/продажи).

## 2. Категории пользователей

В MVP (ЛР1) аутентификация не реализуется; роли описывают предполагаемые сценарии использования одного API:

- **Суперадмин** — управление пользователями и каталогом.
- **Сотрудник** — управление каталогом, составление отчетов.
- **Пользователь** — просмотр каталога, остатков и отчётов (только чтение).

## 3. Сущности и связи

Три связанные каталожные сущности + два журнала движений.

Таблицы:

Продажи
Поле | Тип данных | Примечания
-----|------------|------------
id   | INT     | PRIMARY KEY, AUTOINCREMENT
record_id | INT | FOREIGN KEY
quantity | INT | > 0
unit_price | DECIMAL |

created_at | TIMESTAMP | NOT NULL

Связи:

- `musicians` 1:N `records` (у музыканта много пластинок).
- `genres` 1:N `records` (**одна пластинка — ровно один жанр**; `genre_id` обязателен).
- `records` 1:N `receipts`, `records` 1 — * `sales`.
- Физическое удаление музыкантов и пластинок **не выполняется** (только архивация), поэтому все внешние ключи — `ON DELETE RESTRICT`: история движений неуничтожима.
- «Один музыкант — все жанры его пластинок» — **вычисляемая** связь (не хранится): жанры музыканта = множество жанров по всем его пластинкам (`GET /musicians/:id/genres`).

## 4. Обязательные правила предметной области

1. **Нельзя продать больше, чем на остатке:** при продаже `quantity ≤ records.stock`, иначе отказ (HTTP 409).
2. **Атомарность движений:** продажа и поступление меняют `stock` в одной транзакции (нет частичных изменений).
3. **Снимок цены:** цена продажи фиксируется в `sales.unit_price` на момент сделки; последующее изменение `price` в карточке не меняет уже проведённые продажи.
4. **Поступление** увеличивает `stock` на `quantity`; **продажа** уменьшает `stock` на `quantity`.
5. **Мягкое удаление (архивация) вместо физического:**
   - Музыканты и пластинки не удаляются физически, а **уходят в архив** (`archived_at`). Архивные записи исчезают из основного каталога, но остаются в БД, и история продаж сохраняется.
   - Архивация **музыканта** каскадно архивирует все его пластинки.
   - Из архива можно **вернуть**: восстановление снимает `archived_at`.
   - **Инвариант:** пластинка не может быть активна, если её музыкант в архиве. Восстановление пластинки при архивном музыканте → HTTP 409 (сначала вернуть музыканта).
   - Восстановление музыканта возвращает только его самого; пластинки возвращаются отдельно (осознанный выбор, что вернуть в продажу).
   - С **архивной** пластинкой нельзя проводить движения: ни продажу, ни поступление → HTTP 409.
   - **Жанр** удаляется физически, но только если на него не ссылается ни одна пластинка (включая архивные) → иначе HTTP 409.
6. **Ограничения значений:** `price > 0`, `stock ≥ 0`, `quantity > 0`; `genres.name` уникально и непусто.

## 5. Основные сценарии

1. Завести жанр → музыканта → карточку пластинки (с ценой и жанром).
2. Оформить поступление партии пластинок — остаток увеличивается.
3. Оформить продажу — остаток уменьшается, цена фиксируется снимком; при нехватке остатка — отказ.
4. Отредактировать карточку пластинки / музыканта / жанр.
5. Посмотреть каталог с фильтрами, остатки, жанры музыканта, отчёт по продажам.

## 6. Функции (HTTP API, REST/JSON)

Служебные:

- `GET /health` — проверка живости (без БД).
- `GET /health/ready` — готовность (проверка БД).

Жанры:

- `GET /genres`, `POST /genres`, `GET /genres/:id`, `PATCH /genres/:id`, `DELETE /genres/:id`.

Музыканты:

- `GET /musicians` (фильтр `?archived=false|true|all`, по умолчанию `false`), `POST /musicians`, `GET /musicians/:id`, `PATCH /musicians/:id`.
- `DELETE /musicians/:id` — **архивация** (каскадом архивирует его пластинки).
- `POST /musicians/:id/restore` — возврат из архива.
- `GET /musicians/:id/genres` — жанры музыканта (вычисляемо).

Пластинки:

- `GET /records` (фильтры `?musician_id=&genre_id=&archived=false|true|all`), `POST /records`, `GET /records/:id`, `PATCH /records/:id`.
- `DELETE /records/:id` — **архивация**; `POST /records/:id/restore` — возврат из архива.

Движения:

- `POST /records/:id/receipts` — оформить поступление; `GET /receipts`.
- `POST /sales` (тело: `record_id`, `quantity`) — оформить продажу; `GET /sales`.
- `GET /reports/top-sellers?limit=N` — лидеры продаж: количество, выручка и доля позиции в выручке. Архивные пластинки остаются в отчёте с флагом `archived`.

## 7. Обработка ошибок

Единый формат ответа об ошибке: `{ "error": { "code": "...", "message": "...", "details"?: ... } }`.

- **400 Bad Request** — невалидное тело или параметры запроса (проверка схемой).
- **404 Not Found** — сущность не найдена.
- **409 Conflict** — нарушение бизнес-правила: нехватка остатка при продаже; движение по архивной пластинке; восстановление пластинки при архивном музыканте; удаление жанра, на который ссылаются пластинки; дублирование уникального имени жанра.
- **500 Internal Server Error** — непредвиденная ошибка.

## 8. Требования к хранению данных

### 8.1. Система управления базами данных
Реляционная СУБД **PostgreSQL**; схема создаётся версионированными **миграциями**

### 8.2. Типы данных
- Денежные суммы — `decimal(12,2)`;
- количества и остаток — `int`;
- временные метки — `timestamp` (`created_at`);
- Идентификаторы и внешние ключи - `int`.

### 8.3. Ограничения и индексы
- Все внешние ключи — `ON DELETE RESTRICT` (физического удаления музыкантов и пластинок нет, история движений неуничтожима).
- Архивация хранится как `archived_at timestamptz NULL` в `musicians` и `records`; активные записи — `archived_at IS NULL`.
- Уникальный индекс на `genres.name`; проверки `price > 0`, `stock >= 0`, `quantity > 0`.

### 8.4. Конфигурация
Конфигурация подключения — через переменные окружения; **секреты и локальные файлы не попадают в репозиторий** (`.env` в `.gitignore`, шаблон в `.env.example`).

## 9. Технологии

HTTP API на Node.js + Express, доступ к БД и миграции — Knex, валидация тела/параметров — zod, тесты — Jest + Supertest. Единый интерфейс команд через `make` (setup/run/test/quality/migrate/verify).

## 10.	Требования безопасности
Безопасность функционирования ГУ в обеспечивается выполнением требований к ПОИБ ГУ и услугам по предоставлению инфраструктуры для развертывания ГУ, которые должны быть выполнены в отдельных работах за рамками работ по настоящему техническому заданию.

 ## 11.	Требования к надежности
Должен быть обеспечен отказоустойчивый режим функционирования при круглосуточном режиме работы.
Среднее время восстановления работоспособности компонентов системы не должно превышать 4 часов. В указанное время входит развертывание и настройка специального программного обеспечения на выделенной инфраструктуре, восстановление данных с использованием средств резервного копирования, антивирусная проверка. В указанное время не входит анализ защищенности и выявление причин реализовавшегося деструктивного информационного воздействия.
В системе должно быть предусмотрено:
- контроль целостности данных на уровне СУБД;
- сохранение целостности данных при нештатном завершении программы (отказ рабочей станции и т.п.);
- сохранение работоспособности программного обеспечения при вводе некорректного набора данных оператором.
