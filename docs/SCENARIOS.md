# Как пользоваться API: сценарии

Здесь собраны типовые истории из жизни магазина — от приёмки новой поставки до отчёта по продажам. Каждый пример проверен на работающем приложении, ответы приведены настоящие.

Перед началом поднимите сервер — как это сделать, написано в [README](../README.md#запуск-локально). Дальше считаем, что он отвечает на `http://localhost:3000`.

## Чем отправлять запросы

Примеры даны для `curl`, он есть в Git Bash и в PowerShell. Подойдёт и Postman, и любой другой клиент — важны только метод, адрес и тело.

Чтобы посмотреть, что вообще умеет сервис:

```bash
curl http://localhost:3000/
```

### Важно: кириллица в теле запроса на Windows

Русский текст, переданный прямо в командной строке, до базы доедет испорченным — консоль Windows перекодирует его по дороге:

```bash
# так НЕ надо: в базе окажется мусор вместо «Великобритания»
curl -X POST http://localhost:3000/musicians \
  -H 'Content-Type: application/json' \
  -d '{"name":"Joy Division","country":"Великобритания"}'
```

Положите тело в файл и отправьте файл — тогда байты дойдут как есть:

```bash
# body.json в кодировке UTF-8
curl -X POST http://localhost:3000/musicians \
  -H 'Content-Type: application/json' \
  --data-binary @body.json
```

Латиница в командной строке работает нормально, так что примеры ниже даны в коротком виде. Как только в теле появляется русский текст — переносите его в файл.

## Сценарий 1. Приехала новая поставка

В магазин привезли пластинки исполнителя, которого раньше не было. Нужно завести карточки и поставить товар на учёт.

**Шаг 1. Завести жанр**, если такого ещё нет:

```bash
curl -X POST http://localhost:3000/genres \
  -H 'Content-Type: application/json' -d '{"name":"Post-punk"}'
```

```json
{ "id": 4, "name": "Post-punk", "created_at": "...", "updated_at": "..." }
```

**Шаг 2. Завести музыканта:**

```bash
curl -X POST http://localhost:3000/musicians \
  -H 'Content-Type: application/json' -d '{"name":"Joy Division"}'
```

**Шаг 3. Создать карточку пластинки.** Обязательны название, музыкант, жанр и цена. Остаток можно не указывать — он будет нулевым, товар ещё не оприходован:

```bash
curl -X POST http://localhost:3000/records \
  -H 'Content-Type: application/json' \
  -d '{"title":"Unknown Pleasures","musician_id":4,"genre_id":4,"price":5200.00,"year":1979}'
```

```json
{ "id": 5, "title": "Unknown Pleasures", "price": "5200.00", "stock": 0, "year": 1979 }
```

**Шаг 4. Оприходовать партию** — вот теперь товар появляется на складе:

```bash
curl -X POST http://localhost:3000/records/5/receipts \
  -H 'Content-Type: application/json' -d '{"quantity":15}'
```

```json
{
  "receipt": { "id": 1, "record_id": 5, "quantity": 15 },
  "record": { "id": 5, "title": "Unknown Pleasures", "stock": 15 }
}
```

В ответе сразу видно новый остаток — отдельный запрос за карточкой не нужен.

Разделение на «карточку» и «поступление» намеренное: карточка описывает, **что** это за пластинка, а поступление фиксирует, **сколько** и **когда** её привезли. История поставок остаётся в базе.

## Сценарий 2. Продажа и защита остатка

Покупатель берёт три пластинки:

```bash
curl -X POST http://localhost:3000/sales \
  -H 'Content-Type: application/json' -d '{"record_id":5,"quantity":3}'
```

```json
{
  "sale": { "id": 1, "quantity": 3, "unit_price": "5200.00", "total": "15600.00" },
  "record": { "id": 5, "stock": 12 }
}
```

Остаток уменьшился с 15 до 12, сумма посчитана, цена записана в саму продажу.

Теперь попробуем продать больше, чем есть — на складе 12, просим 100:

```bash
curl -X POST http://localhost:3000/sales \
  -H 'Content-Type: application/json' -d '{"record_id":5,"quantity":100}'
```

```json
{
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "Недостаточно остатка: доступно 12, запрошено 100"
  }
}
```

Ответ — `409 Conflict`. Это главное правило системы: **склад не уходит в минус**. Проверка и списание идут одной транзакцией, поэтому при отказе остаток не меняется ни на единицу — промежуточного состояния, в котором товар списан, а продажа не создана, не существует.

## Сценарий 3. Переоценка

Цену подняли. Меняем её в карточке:

```bash
curl -X PATCH http://localhost:3000/records/5 \
  -H 'Content-Type: application/json' -d '{"price":6100.00}'
```

Продаём ещё две штуки и смотрим историю:

```bash
curl http://localhost:3000/sales
```

```
продажа #2: 2 шт по 6100.00
продажа #1: 3 шт по 5200.00
```

Старая продажа осталась по старой цене. Каждая продажа хранит **снимок** цены на момент сделки, поэтому переоценка не переписывает прошлое: выручка за прошлый месяц не изменится задним числом оттого, что сегодня поменяли ценник.

## Сценарий 4. Снять с продажи и вернуть обратно

Исполнителя решили убрать из продажи. Удаления в системе нет — есть архив:

```bash
curl -X DELETE http://localhost:3000/musicians/4
```

```json
{ "musician": { "id": 4, "archived_at": "2026-09-10T00:22:25.000Z" }, "archived_records": [5] }
```

Музыкант ушёл в архив и **утянул за собой свои пластинки** — в ответе перечислены их идентификаторы. Из каталога они пропали:

```bash
curl 'http://localhost:3000/records?archived=false'   # активные, так по умолчанию
curl 'http://localhost:3000/records?archived=true'    # что лежит в архиве
curl 'http://localhost:3000/records?archived=all'     # всё вместе
```

С архивной пластинкой ничего нельзя делать по складу:

```json
{
  "error": {
    "code": "RECORD_ARCHIVED",
    "message": "Пластинка находится в архиве: движения по ней запрещены"
  }
}
```

Возвращаем обратно. Порядок важен — сначала музыкант, потом его пластинки:

```bash
curl -X POST http://localhost:3000/musicians/4/restore
curl -X POST http://localhost:3000/records/5/restore
```

Если попробовать наоборот, система не даст:

```json
{
  "error": {
    "code": "MUSICIAN_ARCHIVED",
    "message": "Нельзя вернуть пластинку из архива: её музыкант в архиве. Сначала восстановите музыканта"
  }
}
```

Правило простое: пластинка не может стоять в каталоге, если её исполнитель оттуда убран.

Пластинки возвращаются по одной, а не все скопом вместе с музыкантом. Это сделано нарочно: решение «вернуть в продажу» принимается по каждой позиции отдельно.

**Зачем архив вместо удаления.** Продажи ссылаются на пластинки. Если бы карточку можно было стереть, вместе с ней исчезла бы и история продаж — а это уже искажение отчётности. Архив убирает позицию из каталога, но сохраняет всё, что с ней происходило.

## Сценарий 5. Что продаётся лучше всего

```bash
curl 'http://localhost:3000/reports/top-sellers?limit=3'
```

```
Unknown Pleasures     5 шт   27800.00   100.0%
ИТОГО 5 шт на 27800.00
```

Позиции отсортированы по числу проданных копий. У каждой — выручка и доля в общей выручке отчёта. `limit` ограничивает длину списка (по умолчанию 10, максимум 100).

Архивные пластинки из отчёта не выпадают и помечаются `"archived": true`. Так и задумано: они продавались, значит в выручку попали, и прятать их — значит врать в отчёте.

## Сценарий 6. Поиск по каталогу

```bash
curl 'http://localhost:3000/records?musician_id=1'   # всё этого исполнителя
curl 'http://localhost:3000/records?genre_id=1'      # всё в этом жанре
curl 'http://localhost:3000/records?musician_id=1&genre_id=1'   # оба фильтра
```

Отдельно — жанры исполнителя:

```bash
curl http://localhost:3000/musicians/1/genres
```

```json
[{ "id": 1, "name": "Rock" }]
```

Это поле нигде не хранится: система смотрит на все пластинки музыканта и собирает список их жанров. Поэтому оно не может разойтись с каталогом — если у исполнителя появится пластинка в новом жанре, жанр появится здесь сам.

## Что делать, когда пришла ошибка

Ошибки всегда приходят в одном виде:

```json
{ "error": { "code": "КОД", "message": "человеческое описание" } }
```

| Код                                 | HTTP | Что случилось                                                               |
| ----------------------------------- | ---- | --------------------------------------------------------------------------- |
| `VALIDATION_ERROR`                  | 400  | в теле или параметрах что-то не так; в `details` перечислены поля и причины |
| `NOT_FOUND`                         | 404  | нет такой пластинки, музыканта, жанра или маршрута                          |
| `INSUFFICIENT_STOCK`                | 409  | продажа больше остатка                                                      |
| `RECORD_ARCHIVED`                   | 409  | движение по пластинке из архива                                             |
| `MUSICIAN_ARCHIVED`                 | 409  | возврат пластинки, у которой музыкант в архиве                              |
| `GENRE_IN_USE`                      | 409  | удаление жанра, на который ссылаются пластинки                              |
| `ALREADY_ARCHIVED` / `NOT_ARCHIVED` | 409  | повторная архивация или возврат того, что и так в каталоге                  |
| `DUPLICATE`                         | 409  | такое имя жанра уже есть                                                    |
| `INTERNAL_ERROR`                    | 500  | ошибка на стороне сервера                                                   |

Ошибки валидации подсказывают, что именно не так:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректные данные запроса",
    "details": [{ "field": "quantity", "message": "Поле «quantity» должно быть больше нуля" }]
  }
}
```

Разница между 400 и 409 важна: **400** — запрос составлен неправильно, его надо чинить; **409** — запрос понят, но противоречит состоянию магазина. «Продать 100 при остатке 12» синтаксически безупречно, просто товара столько нет.
